# 第一阶段设计与分块状态

本轮只实现配置与命令行，以下持久化设计是下一块的实现方向，不代表已有表或命令。依赖按实际使用加入：当前 Pydantic；下一块 SQLAlchemy、Alembic；解析与获取部分采用 Beautiful Soup（显式 `html.parser`）和同步 HTTPX Client。

## 边界

`config.py` 只读取并校验配置，`cli.py` 负责参数与退出码；导入不启动任务。后续获取器负责 HTTP 和原始响应；Parser 仅接收页面内容与页面 URL，返回结构化列表/正文/附件引用，不访问网络或数据库；存储负责短事务；协调层负责调用顺序及失败恢复，不在数据库事务内等待网络。

## 后续数据模型

稳定身份拟用 `(source_id, source_document_id)`，本站 source_document_id 统一新旧链接中的栏目 ID 和文章 ID。标题、URL、内容摘要都不能代替稳定身份。

通知记录保存发现时间、尝试/成功时间与处理状态；已发现不等于成功处理。失败保留最近成功版本，不允许空结果伪装成功。正文版本独立保存规范化结构与内容 SHA-256、解析器版本及原始响应引用，并用数据库唯一约束保障重复处理幂等。解析器版本参与重解析溯源，具体唯一键在迁移块定案。不预建用户、搜索、推荐、发送或反馈表。

原始响应计划以不可变文件保存于数据目录，数据库保存引用与摘要；规范化内容另存数据库。先完整写入文件再用短事务建立引用，故障可能留下孤立文件，不能留下指向未完成文件的成功记录。304 没有正文，不能当作新原始 HTML。只保留必要响应元数据，不持久化 Cookie 等秘密。正式表演进只通过 Alembic 迁移。

## 对调研建议的调整

列表返回 304 不代表没有待补抓详情或到期复查任务。列表检查与详情处理队列必须独立推进。

“遇到已知通知就停止分页”不能作为完整性的保证；置顶、顺序变化和分页移动会使重叠页策略漏报。普通运行的覆盖范围必须明确，周期完整核对及停机恢复策略将在可靠采集阶段实现。

普通运行关注增量及待处理任务；首次历史导入建立历史基线，不能默认把所有旧通知当作新提醒。未来通知策略需独立决定历史导入、首次发现和正文更新是否触发邮件，本阶段没有发送行为。

## 下一阶段 Parser 任务

- 用现有两个列表 fixture 验证每页 25 条、标题/日期、相对链接及“下页”链；不依赖静态页码规律。
- 统一新式路径和旧式查询参数中的身份，验证置前文章不会被跳过。
- 用两个详情 fixture 提取标题、日期、正文段落/表格、链接和图片引用。
- 提取附件名称和 URL，保留文件标识，不自动下载验证码保护附件。
- 建立空页面、错误页、缺少必要节点和模板变化的失败测试，不把解析失败当作空列表或成功正文。
- 固定规范化规则及解析器版本，验证重复解析输出一致；所有测试离线且不改写 fixture。
