# SignalNest 运行策略：频率、容量与公平性

日期：2026-10-05。范围：现有单源、串行 `crawl_once` 的运行参数及下一步最小政策；不讨论通用爬虫架构、不实现调度或修改生产代码。依据为工作区代码：HEAD `92ddaee` **加当前未提交的采集与恢复验证改动**，不能把这些行为全归于该 commit。未找到适用 AGENTS.md。

## 1. 当前行为与缺口

## 2. 建议起步配置

### 当前CLI可以使用的参数

| 运行 | 触发建议（Asia/Shanghai） | 扫描 / 详情 / 预算 |
| --- | --- | --- |
| 普通轮询 | 每30分钟一次；例如整点及半点 | limited、max-pages=2、max-details=20、max-requests=64、run-seconds=600、resource-seconds=60、body上限2MiB |
| 完整回扫 | 每日一次，建议01:15；与普通启动错开 | full、max-pages=64、max-details=0、max-requests=96、run-seconds=600、resource-seconds=60 |
| 首次/长停机恢复 | 首次先完成一轮full；停机≥24h恢复时先做一次有界full，然后恢复普通轮询 | 同完整回扫；先发现历史ID，再由普通轮询分批补详情；不重放每个错过周期 |

full设max-details=0以保留明确的扫描预算，详情交给普通轮询。01:15只是推荐时段，不是源站维护窗口。full完整覆盖成立后，即使整体收尾出错也不撤销该覆盖事实；full失败不更新last_complete_scan_at/bootstrap_completed_at。原有lock、冷却和退出码继续有效。

合法TOML片段（仅已有HTTP字段）：

```toml
[http]
connect_timeout_seconds = 5.0
read_timeout_seconds = 10.0
request_interval_seconds = 5.0
user_agent = "SignalNest/0.1"
```

现有示例是10/30秒及2秒间隔；上面5秒间隔与已完成实采一致，属于保守起步值，不是站点公布的限速。[实际9次GET与Vary回退](../docs/validation/2026-10-05-live.json)表明：304也可能额外完整获取，不能把每个逻辑任务预算写成恰好一次HTTP。保持稳定User-Agent/profile，减少人为改变表示导致的回退。

```sh
# 显式运行才联网；此报告没有执行这些命令。
signalnest crawl-once --config signalnest.toml --scan limited \
  --max-pages 2 --max-details 20 --max-requests 64 \
  --run-seconds 600 --resource-seconds 60 --max-body-bytes 2097152

signalnest crawl-once --config signalnest.toml --scan full \
  --max-pages 64 --max-details 0 --max-requests 96 \
  --run-seconds 600 --resource-seconds 60 --max-body-bytes 2097152
```

**部署边界：**外部触发串行执行，遇锁占用跳过本次而不是堆积补执行；下个周期继续。时间预算是协作式，运行可能超过600秒，不能据“时段错开”保证不重叠。源冷却期间可跳过新启动，Fetcher仍作最终校验；锁/预算失败不要在同一分钟不断重跑。full失败当前可等下一日固定full或人工处理，普通轮询继续；如果要求自动更早补回扫，再增加单一`last_full_scan_attempt_at`事实并规定重试至少间隔3h，当前run表没存scan_mode，不能从limited/interrupted推断它是full尝试。本次不建设这项调度状态。

### 需要最小代码调整后才生效的政策

这些不是当前可粘贴进TOML的字段（配置拒绝未知字段）：

- 详情分组配额：前景12 / 历史4 / 复查4，批额合计20，允许借空槽。
- 成功复查：发布后0–7天每24h、8–30天每7天、超过30天每30天。
- 失败due：短暂传输/可重试5xx为30min；403/401及TLS校验问题为24h；解析/身份/模板错误为6h；404/410为7天且保留旧版本。429及有效Retry-After始终先服从来源not_before。

下一步只需把这些小政策接入CrawlOptions/CLI或配置，不把建议文档自动变成既定API。当前CLI部署仍是单一24h复查、15min失败和全局due排序，不能宣称新政策已经生效。

## 3. 新通知优先与历史公平：只加批次选择规则

先用现有due门控，再形成互斥三组：

| 组 | 规则 | 保留逻辑尝试数 |
| --- | --- | --- |
| 前景 F | 本次**成功登记**的前两页ID中，last_success_at为空的候选 | 12 |
| 历史补全 H | 其他last_success_at为空的候选，含首次失败、unknown/historical来源 | 4 |
| 到期复查 R | last_success_at非空的候选，含status=failed但有成功基线者 | 4 |

前景是“当前入口可见且尚未成功处理”，并不证明刚发布；置顶旧文仍可获此优先级。full的后续页发现不整体升级为前景；首页304仍解析缓存以取得真实前两页集合。部分坏页不得提取残缺ID；只有一页成功就只使用那一页，首页失败无可信前景时继续H/R。每组沿用`(due或discovered_at,id)`顺序，不按发布日期抛弃任何条目。

**借槽与执行顺序：**先给各非空组保留槽，不足部分释放；剩余槽按F→H→R填充，总数≤20、ID全批去重。执行时先F，再H，再R各一条，之后轮转仍有已分配条目的组直到用完配额，避免先串行跑12个慢前景任务才轮到历史。某组为空就跳过。失败消耗本组一个逻辑尝试，不立即补选同一条；本run最多一次。

这样不需要持久优先级、claim/lease或任务表；前两页集合每次重建。刚发现但已离开前两页的待办会进入H，仍有容量；无法承诺永远保持前景优先。due尚未来到的失败前景不因优先级越过due；页解析/数据库系统错误及来源冷却仍按当前可靠性边界处理。

**公平性是有条件的：**在足够预算、没有全局冷却/系统故障且三组都有候选时，每个完成批次至少尝试H=4、R=4；不是每次一定成功4条，也不是任何异常下都有这个保证。先扫描可能耗尽预算；若频繁发生，应处理full/列表故障或调整有界预算，不能报告“已保留4槽”等同于实际服务4条。

## 4. 容量核算与复查周期

### 4.1 不能只看max_details

设每天实际完成普通运行数为K、每批详情逻辑尝试D，则理论上限`C=K×D`；实际还受列表请求、重试/回退、时间预算、冷却和失败影响。

| 频率、批额 | 理论详情尝试/日 | 若存量约600条、全体每日复查 |
| --- | --- | --- |
| 每60min ×20 | 480 | 连复查都不够，未计新文、历史或失败；必须调整 |
| 每30min ×20 | 960 | 理论剩360，但不等于有360次成功新文容量 |

24页/25条首页/13条尾页来自已有样本；中间页没有全部采样，约600及`23×25+13=588`均为**容量估算，不是实测总数**。当前实采库仅发现25条，因此不能把那个临时库当长期容量样本。

30min频率、三组持续占满时，F/H/R最低分配为576/192/192逻辑尝试/日（假设48个批次完整执行）。600条历史、全部成功、无新发现、持续满载而只能获得4槽时需150轮，约75小时；空槽借用可加快。反复失败、冷却或跳过运行会更慢，不能承诺3天“成功补全”。

普通2页+20详情通常约22个物理请求，5秒间隔给出的间隔成本约105秒；若每项额外一次完整回退约44请求/215秒。24页full+首页复核约25请求/120秒。**这只是间隔算术，未含网络、解析、存储、重试，且不是执行上限**；64/96请求和600秒提供余量，不能保证在最坏重试情形跑满批额。

全部候选都满且无回退时，普通运行约1056 GET/日，另加full约25；不是空闲运行也会请求960详情。全量可见存量与到期频率才决定实际请求数，长期观测前不声称源站允许这个量。没有积压时不填充尚未到期详情。

### 4.2 为什么改成三档复查

年龄按**站点日历日期**计算：`Asia/Shanghai本次处理日期 - ParsedNotice.published_date`。成功due是**本次成功处理UTC时间+对应间隔**，200与有效304相同；不要从原200 fetched_at或HTTP Last-Modified起算。未来发布日期按近期档24h并记录异常计数，不删除/拒绝已通过Parser的通知。

- 0–7天：24h；更容易涉及近期报名/名单修订。
- 8–30天：7d；接受最多约一周加排队的更新发现延迟。
- >30天：30d；接受旧文修订最多约一个月加排队，不能宣传实时旧文监控。

这只是起步取舍，网站修改频率未知。若约600条都已超过30天，平均需求约20次复查/日；示例`20条近期+40条中期+540条旧文`需求为`20+40/7+540/30≈43.7次/日`，是假设分布下的估算，不是当前站点统计。不得把平均值等同于当天峰值：集中补全会在相同日期形成due波峰，依靠稳定排序与批次跨运行分摊，逾期仍必须保留。

无需给documents加发布日期列：成功解析已有日期，现有版本也保留它。最小调整是在解析后、同一成功事务前计算due，传给已有`save_notice_in_transaction`；当前协调器提前传固定`at+86400`，必须调整这条调用路径或增加窄的due计算回调。不能先提交成功再另一个事务修改due。失败due同样按有限错误类型映射，存储/失败登记不可用仍终止，不能仅延期掩盖系统故障。

政策升级不会自动修改旧next_due_at；首次上线新政策时，用已成功版本的日期显式重算，**已逾期任务不往后推**（取旧due与新due较早者），失败due不批量清除。本次不增加指数失败计数、随机调度或通用政策引擎。

## 5. 观察项与具体验收

先按建议运行一周观察，再决定是否提高容量。每批在现有摘要旁增加F/H/R的尝试/成功/失败/到期剩余及最老逾期时长；历史积压按`last_success_at=NULL`统计，不能用remaining_unprocessed代替（它含带成功版本的复查失败）。记录当前前两页识别依据，不把首页失败当作没有新通知。

运维提示建议：超过26h没有完整扫描成功、历史最老首次待办超过72h且多次未获得4次服务、复查最老due逾期超过24h、普通运行连续3次请求/时间预算截断，输出简短原因。source冷却单独展示，不能建议更密集重跑来抵消它。这些是观察阈值，不是已实现告警或邮件。

| 场景 | 具体验收结果 |
| --- | --- |
| 100条更早历史待办+1条前景首次通知 | 首个详情尝试是前景；该批剩余槽借给H，不因旧discovered_at把新文推到末尾。 |
| 连续10轮F≥12、H≥4、R≥4且预算充分 | 每轮12/4/4，总计H至少40、R至少40；按逻辑尝试计，失败也占槽。 |
| 一组/两组为空 | 借空槽至其他due候选；总尝试≤20、无重复、不得拉未到期复查填槽。 |
| 前景首次失败due尚未来到；failed有成功基线 | 前者不选；后者归R，不占首次历史槽；旧版本保持。 |
| full发现后续旧页；首页304；首页坏模板 | 后续页归H，304成功前两页可重建F；坏页不产生F，可按已确认页与DB待办继续。 |
| 重启且未成功条目仍在前两页 | 重新归F，first_discovery_run/origin不变；离开前两页则进入H而非丢弃。 |
| 成功处理年龄7/8/30/31天、未来日期 | due依次为+24h/+7d/+7d/+30d/+24h；用上海日期划档、UTC秒持久化；304按当前处理时间计算。 |
| 新政策上线，旧due已逾期/失败due未来 | 不把逾期往后移、不抹除失败退避；处理与due同事务回滚/提交。 |
| 403/ParseError/404/ConnectTimeout | 新政策分别+24h/+6h/+7d/+30min，不同于当前统一900秒；下一次实际执行还受外部周期约束。 |
| 429长Retry-After，或批次中预算耗尽 | 源冷却保留，全部组停止后续网络；可少于保留槽，报告未服务数，不能新开一次run立即追打。 |
| 定时启动时旧run仍持锁、长停机恢复 | 新启动跳过/明确锁拒绝，无堆积；恢复只做一次有界full，不重放错过每半小时的运行。 |
| full限额中断/失败，下一次普通运行 | last_complete保持，普通2页与详情待办仍推进；不能按result=0或limited当完整成功。 |
| 按小时20条、600条每日复查的容量输入 | 容量校验明确显示480<600，不把有限测试通过等同于稳态可持续。 |

**本次交付是政策与验收设计。**未改src/tests/config/已有研究，未运行测试、请求校园页面或配置自动任务；优先补分组选择、按日期同事务设due及必要统计，再开始低频定时观察。24页边界与到期稳定性以已有验证为依据，长期站点负载、真实修订频率和收敛速度仍未知。
