## 调度、尝试与重试

**源码确认。** 普通模式的 ticker 每秒扫描 watch；默认周期来自全局设置（3 小时），watch 可覆盖。到期判断以 `now - last_checked` 为基础，并受时间窗口、暂停、全局最小检查秒数和可选 jitter 影响。扫描优先考虑 `last_checked` 最早的 watch；已运行或已在队列中的 UUID 不再由 ticker 加入。每个代理另有进程内 `reuse_time_minimum` 间隔。源码没有全局同域并发/频率预算或严格公平保证。[Ticker 扫描、排序和到期条件](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/flask_app.py#L1383-L1562) · [watch 运行中/队列中去重](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/flask_app.py#L1417-L1559)

worker 在抓取前把 `last_checked` 设为本次尝试开始时间；完成或捕获异常后更新 watch。它不是“最近成功时间”。一个慢任务在 `running_uuids` 中时不会被 ticker 重复入队；任务结束后，如果按尝试开始时间计算已经到期，可以很快再次调度。源码可确认的显式重抓入口是启动参数 `-r all` 或 `-r UUID,...`：进程初始化后把对应 watch 以 priority 1 入队。`-r ... N` 的重复循环由 batch monitor 驱动；普通服务的 UI 手动检查入口本次未确认。重复 UUID 被 worker 认领时会延迟后重新排队；这不是 HTTP 重试。[尝试开始与异常处理](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/worker.py#L145-L263) · [认领冲突与延迟重排](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/worker.py#L84-L101) · [`-r` 解析和 enqueue](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/__init__.py#L231-L248) · [priority 1 与 batch 重复](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/__init__.py#L408-L442) · [batch 重复循环](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/__init__.py#L472-L534)

Requests fetcher 用 `urllib3.Retry` 包装一次 `requests.Session` 请求：`total/connect/read` 设为环境变量 `REQUESTS_RETRY_MAX_COUNT`，缺省 6；`status=0`，退避因子 0.5，允许方法包含 HEAD、GET、OPTIONS、POST。因而连接/读取传输异常可以在一次任务内重试，HTTP 状态码不会由此策略重试；注释仍说默认 3 次，与可执行默认值 6 不一致。[请求重试配置](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/content_fetchers/requests.py#L58-L79)

重试耗尽后，当前任务退出并记录 `last_error`；没有失败专用退避，也没有 worker 把失败项立即重新入队。之后仍由常规 ticker 按 `last_checked` 和周期重新判断到期。worker 的异常后短暂停顿只让出执行时间，不构成重试策略。[worker 错误处理和成功清错](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/worker.py#L240-L313) · [ticker 到期时间计算](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/flask_app.py#L1499-L1559)

**线程恢复是另一层。** ticker 发生未预期异常或返回会由 supervisor 重启；源码初始化 `backoff=1` 后在短周期失败时先翻倍再等待，所以第一次短周期失败实际等待 2 秒，之后 4、8…最多 60 秒；成功运行达到 60 秒时重置为 1 秒。worker 在 10 个任务或 3600 秒后主动返回 `restart`，pool 立即重启 coroutine；意外异常由 pool 等 5 秒后再运行。健康检查每 60 秒检查并补建死掉的 worker thread。这些机制不等于重新执行刚才出队的 watch，不能替代请求重试或持久化任务记录。[ticker supervisor](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/thread_supervisor.py#L73-L106) · [worker restart](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/worker_pool.py#L134-L164) · [worker restart 上限](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/worker.py#L68-L69) · [worker restart 条件](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/worker.py#L758-L764) · [health check 周期及替换](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/flask_app.py#L1398-L1413) · [worker 数量恢复](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/worker_pool.py#L568-L623)

重启不会从队列日志重放错过的每个周期：两个队列都在内存中。正常启动重新加载 watch 后，ticker 只会按持久化的 `last_checked` 重新评估当前是否到期；启动 CLI 的 `-r all` 是显式强制重抓选项，不是周期补账。[内存队列定义](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/queue_handlers.py#L14-L50) · [启动 `-r all` 路径](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/__init__.py#L408-L442) · [状态加载](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/store/__init__.py#L194-L252)

**配置更新边界。** processor 创建时 deepcopy watch；HTTP 参数从这个副本与随后读取的全局设置组装。比较阶段 worker 又传入 datastore 中的 live watch，过滤器读取当前 tag/global 配置。因此一次任务没有绑定统一配置版本；运行中编辑可能让请求配置和比较规则来自不同时间点。源码没有任务开始时锁定的配置快照或版本校验。[processor 的 watch 副本](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/processors/base.py#L35-L46) · [请求参数来源](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/processors/base.py#L183-L280) · [worker 传 live watch](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/worker.py#L180-L199)

**浏览器接口事实。** Playwright 路径接收 timeout、headers、method/body 等参数；连接 CDP 使用固定 60 秒连接 timeout，页面/上下文/浏览器在 `finally` 尝试关闭，关闭单项限制为 5 秒。worker 结束时还会调用 fetcher `quit()`。页面等待超时会记录后继续，而非都转成请求失败；非 200 与空页再按错误处理。[Playwright 请求与 CDP](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/content_fetchers/playwright.py#L249-L321) · [页面等待和资源关闭](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/content_fetchers/playwright.py#L349-L398) · [关闭资源及 worker 清理](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/content_fetchers/playwright.py#L454-L490) · [worker finally](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/worker.py#L683-L715)

**通知保证边界。** 源码中有 notification count/error 字段，但没有持久化 outbox、每个 history version 的发送状态或唯一事件键。snapshot/index 成功后、queue enqueue 前崩溃可丢提醒；通知已被外部服务接受但本地进程在记录结果前退出时，app 无法证明送达结果。源码没有建立 exactly-once 或重启后的可靠补发；因没有可见的版本级去重记录，后续重抓/重新处理也不能保证不重复。[通知计数与 enqueue](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/notification_service.py#L464-L473) · [volatile queue 与 runner](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/flask_app.py#L1319-L1381)

## 崩溃边界与可观察后果

下表的“推断”严格来自已确认的写入顺序，**本次没有对上游进程作故障注入**。

| 崩溃点 | 推断的落盘状态 / 后果 |
| --- | --- |
| HTTP 请求完成前 | 队列任务随进程消失；如果尝试时间还没持久化，重启按旧 `last_checked` 计算，可能很快再抓。重启只重新判断当前到期性，不逐周期回放。 |

watch JSON 的“写临时文件再 replace”是单文件原子替换，不是跨文件事务。历史快照单独原子写入、index 另行追加，raw checksum 又是直接覆盖文件；因此这些原子操作不足以保证一次 check 的整体一致性。history 测试验证正常执行后的索引与 snapshot 对齐，没有验证上述边界断电时恢复。[文件替换实现](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/changedetectionio/store/file_saving_datastore.py#L66-L125) · [history consistency 测试](https://github.com/dgtlmoon/changedetection.io/blob/593e9cc48c2b475dacbc3dbdebe2f5136bef8efa/tests/test_history_consistency.py#L12-L140)
